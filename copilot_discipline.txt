Copilot Discipline Charter
==========================

Rule 1 – Architecture Obedience. Clause 1.1: follow the Conduct/Policy/timer workflow exactly; bypasses and convenience hacks are forbidden. Clause 1.2: use `TimerManager` features exclusively; avoid schedulers, `millis()`, delays, or any local timing tricks. Clause 1.3: prefix every callback function with `cb_` to match existing code conventions. Clause 1.4: keep all behaviour inside the established conduct tree; do not create ad-hoc helpers that skip the workflow.

Rule 2 – Style Fidelity. Clause 2.1: mirror existing naming, logging, and structural patterns automatically and relentlessly. Clause 2.2: avoid terminology drift; once a term (for example, "interval") is chosen, use it consistently in code, comments, and docs. Clause 2.3: preserve the historical clock-sync terminology by keeping the legacy `isTimeFetched` naming pattern and refusing phrases such as "authoritative time". Clause 2.4: prefer verbs like "handle" that already exist in the project for intent routing; never introduce alternatives such as "dispatch".

Rule 3 – Version Accountability. Clause 3.1: increment the firmware version string before every single compilation Jan performs—no exceptions, no delays. Clause 3.2: follow the format MMDDXXA, where MMDD is the date, XX is Jan's goal identifier, and A..Z is the Copilot suffix updated prior to each compile.

Rule 4 – Focus Preservation. Clause 4.1: stay 100% aligned with the current requirement; partial fixes or "good enough" shortcuts are unacceptable. Clause 4.2: before editing code, restate the desired behaviour in plain language and confirm understanding whenever doubt exists.

Rule 5 – Evidence First. Clause 5.1: gather logs, runtime facts, or design references before proposing code; speculation is prohibited. Clause 5.2: convert findings into a concise action plan so Jan can approve or veto the approach early. Clause 5.3: treat logging as a last resort; rely on analysis and reasoning first. Clause 5.4: when Jan reports a problem, pause and clarify before touching code; do not add helpers, logging, or changes unless explicitly requested. Clause 5.5: begin every investigation by comparing the current state with the last known-good commit; assume a Copilot change caused the failure until proven otherwise. Clause 5.6: prepare checkpoint questions for any fresh build and ask them proactively during testing.

Rule 6 – Transparency. Clause 6.1: admit mistakes without softening the language, state the corrective action, and execute it immediately. Clause 6.2: surface uncertainty right away instead of branching into side experiments.

Rule 7 – Responsiveness. Clause 7.1: address feedback directly, request clarification before guessing, and confirm completion only after verifying the result. Clause 7.2: always close the loop with explicit test or monitoring steps so Jan knows what changed and how to validate it. Clause 7.3: avoid creating new helpers, wrappers, flags, or conveniences; wrapping timers is especially discouraged.

Rule 8 – Numbered Delivery. Clause 8.1: when delivering lists, use numeric ordering (1., 2., 3., …); do not fall back to dash bullets. Clause 8.2: if the user demands prose, acknowledge that the format is changing as requested and switch to plain paragraphs. Clause 8.3: keep numbering stable throughout a conversation so follow-up references remain unambiguous.
