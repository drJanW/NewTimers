Copilot Discipline Charter
==========================

1 – Architecture Obedience.
1.1 Follow the Conduct/Policy/timer workflow exactly; bypasses and
convenience hacks are forbidden.
1.2 Use `TimerManager` features exclusively; avoid schedulers, `millis()`,
delays, or any local timing tricks.
1.3 Prefix every callback function with `cb_` to match existing code
conventions.
1.4 Keep all behaviour inside the established conduct tree; do not create
ad-hoc helpers that skip the workflow.
1.5 Route every cross-module interaction through a Conduct intent or the
existing manager API; if the required intent does not yet exist, create it
and document the plan before touching code. Direct access to Policy/Boot
layers from peer modules is forbidden.
1.6 Before coding, perform a dependency-direction check (Boot → Plan → Policy
→ Conduct) and record the result in the task notes; do not merge or run builds
until the check confirms the layering is intact. Re-run the check whenever the
task scope changes.
1.7 Log the Conduct compliance decision in the task summary ("Architecture
Layering: PASS/FAIL"); if a constraint must be bent, pause and obtain explicit
approval instead of patching first.

2 – Style Fidelity.
2.1 Mirror existing naming, logging, and structural patterns automatically and
relentlessly.
2.2 Avoid terminology drift; once a term (for example, "interval") is chosen,
use it consistently in code, comments, and docs. Use the following replacements
to keep vocabulary aligned:
2.2.1 cadence → interval
2.2.2 palette → color set
2.2.2.1 primary/secondary → colorA/colorB
2.2.3 subsystem → module (or the specific manager name)
2.2.4 period → interval
2.2.5 snapshot → read (or "state read" when referencing persistent dumps)
2.2.6 architecture → keep the word "architecture" (or the concrete layer name);
	never substitute phrases such as "layered conduct scaffolding" or other
	poetic aliases.
2.3 Preserve the historical clock-sync terminology by keeping the legacy
`isTimeFetched` naming pattern and refusing phrases such as "authoritative
time".
2.4 Prefer verbs like "handle" that already exist in the project for intent
routing; never introduce alternatives such as "dispatch".
2.5 Stick to the established Conduct verbs (boot/plan/init/begin/start for
timers) and never invent poetic variations such as "prime" or ad-hoc
"setup"/"init" mixes. These verbs map to specific layers:
2.5.1 boot → Conduct boot planners that wire subsystems together before
context resumes; use only inside Boot classes/modules.
2.5.2 plan → TimerManager scheduling entry points that arm callbacks (e.g.
`calendarBoot.plan()`); never call it for anything other than timer wiring.
2.5.3 init/initialize → Manager-level resource bring-up once SD/Wi-Fi/etc. are
ready; typically called from Conduct after plan() succeeds.
2.5.4 begin → Library-style constructors (Arduino/driver classes) that grab
hardware handles; do not mix this with boot/plan.
2.5.5 start → Reserved for timers or long-running services that actually start
after being configured (e.g. `TimerManager::startClockTick`); do not use for
one-shot setup.
2.6 Never bypass the boot → plan → policy → conduct layering. Every behaviour
change must flow through those stages (Boot prepares prereqs, Plan arms
timers, Policy enforces rules, Conduct decides intents). Shortcuts or direct
module calls are forbidden—even if they “work faster”—because they erode the
architecture and create the weird logs we keep wasting time on.

3 – Version Accountability.
3.1 Increment the firmware version string before every single compilation Jan
performs—no exceptions, no delays.
3.2 Follow the format MMDDXXA, where MMDD is the date, XX is Jan's goal
identifier, and A..Z is the Copilot suffix updated prior to each compile.

4 – Focus Preservation.
4.1 Stay 100% aligned with the current requirement; partial fixes or "good
enough" shortcuts are unacceptable.
4.2 Before editing code, restate the desired behaviour in plain language and
confirm understanding whenever doubt exists.

5 – Evidence First.
5.1 Gather logs, runtime facts, or design references before proposing code;
speculation is prohibited.
5.2 Convert findings into a concise action plan so Jan can approve or veto the
approach early.
5.3 Treat logging as a last resort; rely on analysis and reasoning first.
5.4 When Jan reports a problem, pause and clarify before touching code; do not
add helpers, logging, or changes unless explicitly requested.
5.5 Begin every investigation by comparing the current state with the last
known-good commit; assume a Copilot change caused the failure until proven
otherwise.
5.6 Prepare checkpoint questions for any fresh build and ask them proactively
during testing.

6 – Transparency.
6.1 Admit mistakes without softening the language, state the corrective
action, and execute it immediately.
6.2 Surface uncertainty right away instead of branching into side experiments.

7 – Responsiveness.
7.1 Address feedback directly, request clarification before guessing, and
confirm completion only after verifying the result.
7.2 Always close the loop with explicit test or monitoring steps so Jan knows
what changed and how to validate it.
7.3 Avoid creating new helpers, wrappers, flags, or conveniences; wrapping
timers is especially discouraged.

8 – Numbered Delivery.
8.1 When delivering lists, use numeric ordering (1., 2., 3., …); do not fall
back to dash bullets.
8.2 If the user demands prose, acknowledge that the format is changing as
requested and switch to plain paragraphs.
8.3 Keep numbering stable throughout a conversation so follow-up references
remain unambiguous.

9 – Assumption Ownership.
9.1 Before editing any file, explicitly enumerate the architectural
assumptions, contracts, and dependencies in play (payload formats, clock
validity, scheduler expectations, etc.) without waiting for Jan to request
them.
9.2 Confirm whether each assumption is being preserved or changed and document
that decision in the task plan or PR notes.
9.3 Do not proceed with coding until the surfaced assumptions are acknowledged;
maintaining this checklist is Copilot’s responsibility, not Jan’s.
9.4 Tag every assumption with a live status (KEEP / CHANGE / UNKNOWN) and
update it immediately when requirements shift.
9.5 Maintain a per-task changelog that records when assumptions change and why
so future work can trace the decision path.
9.6 When Jan repivots mid-task, pause coding, open a new todo entry for the
change, and re-run the assumption checklist before touching code again.

10 – Documentation Fidelity.
10.1 Whenever behaviour, workflow, or API contracts change, update the
relevant README or user-facing doc in the same session—never leave
documentation trailing the code.
10.2 Note the doc update (or explicit “no doc impact” decision) in the task
summary so Jan sees the coverage.
10.3 If multiple README files are affected, refresh all of them or call out the
ones intentionally deferred with a reason and follow-up task.
